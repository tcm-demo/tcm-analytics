价格审批模块 需求说明

模块路径：库存管理 / 价格审批（pages/price-approval.html） 版本：v1.0　日期：2026-09-11 设计决策与推演过程见《采购定价与入库价格管控说明》，本文只写"做什么、规则是什么"，不重复论证。

0. 版本更新记录

版本 日期 说明
v1.0 2026-09-11 首版。入库审批队列（15 价格异常 / 25 待入库审核）、整单级判定口径、审批人四动作、动作二次确认、低价知会台账、演示数据与重置。

1. 背景与目标

入库价格校验是硬性的：送货价与定价不一致、或商品未定价，单据就不能直接入库。但现实里总有例外——现场议价、送错规格、新商品来不及定价。审批模块就是这条唯一的例外通道。

三条底线：

  1. 一次入库只审一次：价格差异和单据内容在同一个界面给结论，不让店员为同一车货等两次审批。
  2. 系统规则优先于人工：审批人只能在规则允许的范围内决定，配成「禁止入库」的单不会被审批放行。
  3. 不可逆动作必须二次确认：批准 / 驳回 / 拒收都是单据级、改了就回不来的操作，点下去之前必须让审批人看清后果。

4. 详细功能需求

4.1 单据状态

状态 名称 含义
10 待提交 录入中/被驳回，可编辑后重提
15 价格异常 命中「审核后入库」规则，库存未增加
25 待入库审核 价格无异常，但门店开了「入库审核」开关，库存未增加
20 已完成 审批通过，库存已增加
30 已拒收 终态，库存不增加，单据保留供与供应商对账

15 与 25 是入审批队列的两种来源，队列按两张状态一起查，行内以状态徽标区分。

4.2 队列构成：什么单据会进来

闸门 触发条件 单据状态 库存
入库审核开关 = 开 门店配置项，价格全对也拦 25 待入库审核 整单不动
高/低价 = 审核后入库 任一行价格命中 audit 15 价格异常 整单不动
未定价 = 审核后入库 任一行未定价且配 audit 15 价格异常 整单不动
高/低价 = 禁止入库 任一行命中 forbid 提交端拦截（09-11 定稿）：单据不能提交，留在 10 待提交，提交时点名提示 整单不动
都不触发 — 20 已完成 提交即入

forbid 为什么不进队列（09-11 修订）：命中「禁止入库」的单即使提交上来也注定不会被审批放行，挂在队列里只会让审批人第一次点击就吃拦截提示。因此 forbid 在提交端拦截——单据留在「待提交」，提交人当场看到点名提示，去维护定价或调整商品后重新提交。审批页的重算守卫保留为兜底（应对提交后定价被删除/改严的边缘场景）。存量已挂在队列里的 15-forbid 单，加载时自动退回「待提交」（库存从未增加，安全流转）。

队列列表列：序号 / 入库单号（可点开详情）/ 日期 / 门店 / 供应商 / 波动 / 状态 / 异常说明（逐条列出命中规则的商品与原因）。

4.3 判定是整单级的，不是行级挂起

  • 校验对每个商品行独立出结论，但结论汇总到单据：任一行命中 block（audit 或 forbid），整单 pass = false、状态置 15。
  • 库存写入只有一个入口——单据最终状态为 20 时才落批次。所以合规行不会"先溜进去"，它跟着本单一起等。
  • 审批同样是整单动作：status = 20 + 整单加库存。

为什么不做行级挂起：库存记的是仓库实收实物，单据与实物必须一一对应。若合规行先入、异常行挂起，一旦异常行最终被拒收或驳回，这张单的成本、批次、与供应商的对账口径就裂成两半，没法解释。一次入库只审一次也是同一原因。

部分入库的出口是拆单，不是行级挂起：驳回 → 单据回 10 待提交 → 编辑中删掉异常行（或拆成新单）→ 合规部分重提直接入库；异常商品另建一张单走审批或拒收。两张单各自完整，口径不裂。

4.4 审批人的四个动作

动作 效果 适用场景
按入库价批准（原「批准原样」，09-11 更名） 按单据入库价（送货价）整单入库；默认定价表不动，可选勾选「同步更新定价」把入库价写入当前段 价格确实合理只是需要人确认；供应商确已调价、按新价正常收货时勾选同步，下次同价进货不再拦截
仅本次改价入库 审批人改本次入库价，入库存、记成本；默认定价表不动，可选勾选「同步更新定价」把改后价写入当前段 送错规格、按错档送；现场议定按中间价收，下次仍按原定价校验。供应商确已调价时勾选同步
驳回 退回 10 待提交，库存不变，可改后重提 不接受这个价
拒收 置 30 终态，库存不增加，单据保留对账 货不对、价谈不拢，整单不要了

规则优先于人工（09-10 落地，09-11 前移到提交端）：「禁止入库」在提交时即拦截——命中 forbid 的单根本提不上来。审批页的重算守卫保留为兜底：按入库价批准 / 仅本次改价在放行前会重算整单校验，改价后仍命中「禁止入库」的行（含未定价禁入）不放行（场景：提交后定价被删除或规则改严）。audit 行可批，forbid 行不可批。

一单多商品按行独立判定（09-10）：一次入库是一车货，异常往往不止一个。forbid 行拦整单（提示只点名 forbid 行，不误伤 audit 行）、audit 行可批、entry_only 行照常入库并记知会、合规行无感。整单放行时新产生的低价差异会补记知会（同单同商品同价不重复）。定价按「商品 + 门店 + 供应商」隔离查价——单内商品必须都是该供应商体系，跨供应商的商品会判「未定价」，所以采购单天然按供应商分开建单。

"仅本次"与"同步更新定价"的边界（09-11 补充，09-11 晚扩到两条批准路径）：改价后入库默认只影响这一笔，基准价变更历来要求另走调价单。但真实场景中供应商确已调价（长期生效）时，审批人明知基准过时却只能"仅本次"，定价表会持续滞后。因此 09-11 起在「仅本次改价入库」弹窗提供显式勾选项「同步更新定价（写入当前段）」；同日发现「按入库价批准」路径存在同样缺口（按新价收货但定价不动，下一张同价单还会被拦），故该路径也提供同款勾选项。勾选后才把确认价写入定价表当前段，旧段自动归档写历史（留痕 updatedBy=审批改价同步，生效起=当天）。护栏：① 默认不勾选，品质差异等一次性价差不勾；② 仅同步"商品+门店+供应商"三要素都能命中、且与当前定价确有差异的记录，未定价/供应商不一致的商品跳过并在确认框中明示（需到采购定价模块处理）；③ 同步动作随二次确认一并列出（"同时更新采购定价 N 项"），确认一次即同时生效，不产生二次弹窗。

4.5 审批动作的二次确认（09-11 落地）

批准 / 驳回 / 拒收都是单据级、不可撤销的状态流转，点击后立即重算并落库。因此每一个动作都先弹确认，且确认框里写清后果，不做"点一下就走"：

动作 确认框给出的信息
按入库价批准 先弹小窗：逐行列「定价 vs 入库价 + 对比」+「同步更新定价」勾选项；点「下一步」后再出一次确认（门店、供应商、商品项数、批准后合计金额，并声明"整单立即计入库存，不可撤销"）
仅本次改价入库 弹窗内实时显示「原件合计 → 改后合计 + 已修改 N 项」+「同步更新定价」勾选项；点「确认入库」后再出一次确认，逐条列出改动（如 娃娃菜 ¥3.20 → ¥2.80）+ 合计；勾选同步时写明「同时更新采购定价 N 项」及跳过项
驳回 声明"退回待提交，库存不变，提交人可修改后重提"
拒收 声明"拒收为终态：库存不会增加，单据保留供对账，之后不能再审批"

两条实现口径：

  • 规则优先于确认：二次确认放在整单校验之后。若本单仍命中「禁止入库」规则，先提示拦截、不弹确认框——避免审批人确认半天最后被规则挡回。校验用影子单预演（把本次改价套到副本上算），取消确认时原单的价格、金额、知会零污染。
  • 详情页「提交入库」同样确认，且确认文案随校验结果变化：合规 → "提交后整单立即计入库存"；开着入库审核 → "需审核通过才计入库存"；价格异常 → "库存不会增加，将置为价格异常待审批"。

同类动作一并确认（同为不可逆库存变动）：调拨单的「调拨发货」（扣减调出方库存）与「确认完成」（增加调入方库存）。

4.6 低价知会台账

低价差异（配 entry_only / 配 audit 但被批准）以及未纳入定价的行，都进知会台账留痕：

  • 列：序号 / 入库单号 / 门店 / 供应商 / 商品 / 定价 / 实收价 / 差异 / 状态（待处理 / 已处理）。
  • 知会不阻塞入库——货照收，但差异必须留痕，供复盘供应商。
  • demo 现状：知会仅展示与留痕，尚无「标记已处理 / 纳入定价」动作，正式版补齐（见 9. 非目标）。

4.7 演示数据与重置

  • 审批页预置覆盖各规则分支的演示单据（audit 可批、低价知会、未定价、合规待审核、一单多商品混三种结果；另有 forbid「提交被拦」演示单留在待提交列表）。
  • 演示场景自带定价夹具：按演示单的供应商体系 upsert 场景所需定价与管控配置，不依赖本机存量数据，避免"被练手改坏后全变未定价"。
  • Tab 栏右侧「↺ 重置演示数据」：确认后清空入库单与知会、重新注入演示数据，并把演示涉及的价格与管控配置恢复为演示基准（范围外数据不动）。演完一遍可重置重看。

5. 业务规则

编号 规则
R1 校验在库存变动之前执行，不存在"先入库后补票"
R2 任一行命中 block → 整单 15，库存不动
R3 库存写入唯一入口：单据最终状态 = 20
R4 forbid 行在提交端拦截（单据留 10）；audit 行可批准。审批重算守卫兜底 forbid 不可放行
R5 改价仅作用于本单，不改定价表
R6 已批准改价后重算通过 → 整单放行，新产生低价差异补记知会（去重）
R7 驳回 ≠ 拒收：驳回可重提；拒收为终态
R8 每个审批动作执行前二次确认；被规则拦下时不弹确认
R9 取消确认 = 零副作用（价格、金额、知会均不变）
R10 加急只影响处理优先级，审批通过才入库

7. 权限

  • demo 现状：菜单级授权——有价格审批页权限即可操作，尚无独立的审核权限点（"能进页面" = "能审"）。
  • 正式版：拆出 inv_entry.audit 权限点，把"能看"和"能审"分开，与 R104 采购经理 角色一并落地；无 audit 权限的用户打开审批页只能看、不能审。

8. 验收标准

  1. 命中 forbid 的单在提交时即被拦截：单据留在待提交，提示点名 forbid 行与原因；审批队列不出现该单。存量 15-forbid 单加载时自动退回 10（库存不变）。
  2. 点「按入库价批准」→ 弹小窗（定价 vs 入库价 + 同步勾选）→ 勾选同步 → 弹确认（含门店/供应商/项数/批准后合计 + "同时更新采购定价 N 项"）→ 取消 → 状态、价格、金额、知会、定价表全部不变。
  3. 确认批准 → 状态 20、库存按整单增加、记录审批人。
  4. 「仅本次改价入库」弹窗内改价 → 实时显示「原件合计 → 改后合计 + 已修改 N 项」→ 确认后明细列出改动 → 默认放行后定价表价格不变；勾选「同步更新定价」后放行，定价表当前段更新为改后价、旧段写入历史（closedBy=调价(审批同步)）。
  5. 改价后仍命中 forbid → 不放行，提示先更新采购定价或驳回/拒收。
  6. 驳回：确认后状态 10，库存不变；取消则状态不变。
  7. 拒收：确认后状态 30，库存不增加，页面不再提供审批动作。
  8. 详情页「提交入库」确认文案随校验结果变化（合规 / 开审核 / 价格异常三种）。
  9. 一单多商品混 audit + forbid + entry_only + 合规：拦截提示只点名 forbid 行；改价放行后低价知会补记且不重复。
  10. 「重置演示数据」确认后，审批队列与知会恢复演示基准，范围外的定价/档案/配置不受影响。

9. 非目标（Non-goals）

不做 原因 替代方案
行级挂起（合规行先入、异常行单独挂起） 单据与实物必须一一对应；行级挂起会撕裂成本/批次/对账口径，需把单据状态下沉到行 驳回 → 编辑拆单（4.3）
先入库后补定价 与"校验在库存变动之前"直接冲突 加急审批（R10）
审批里隐式改定价表 会让定价表被架空 同步更新定价必须显式勾选（默认不勾，见 4.4 边界说明）；基准价变更的常规路径仍是调价单
知会处理动作（标记已处理 / 一键纳入定价） 本期只做留痕 正式版补齐（4.6）

10. 名词解释

名词 含义
定价 / 协议价 与供应商事先协定的采购价，存定价主表
送货价 / 进货价 送货单上实际填报的价格
15 价格异常 命中价格规则、库存未增加的单据状态
25 待入库审核 价格合规但门店开了入库审核、库存未增加的单据状态
forbid / 禁止入库 规则档位之一：该行不可入库；提交端即拦截，审批重算守卫仅作兜底
audit / 审核后入库 规则档位之一：该行需审批通过才入库
entry_only / 仅入库 规则档位之一：不阻塞入库，但记低价知会

一、结论：只区分效期，不区分商品

所有商品都有「效期」，只有两种：

效期类型 含义 典型商品 存储值
不计效期（永久效期） 无明确保质期，或虽有保质期但不影响使用 / 不参与经营决策 蔬菜、散装水果、散装肉禽、鲜活水产；纸品、纸尿裤、日化、毛巾碗筷 exp = '9999-12-31'
按效期管理 有明确保质期，且保质期影响经营决策，需按到期日管理 包装食品、乳品、饮料、酒类、粮油调味、冻品、盒装蛋 exp = 生产日期 + 保质期（YYYY-MM-DD）

永久有效也是一种效期——只是相对其他分散效期更长、且日期固定而已。

不再需要判断"这是食品还是百货""是不是称重商品"。商品档案上只有一个开关：计不计效期。

这是经营决策，不是商品属性。 本质是：这个商品有没有有效期概念？客户想不想按效期维护？不想按效期，就不设效期，商品只关注总数、不涉及效期概念。

同一件商品，A 店想按效期管、B 店只想管总数，各自设置即可。系统只认开关，不认品类。

两个必须分开的概念：保质期（事实） vs 按效期管理（决策）

是什么 字段 由谁决定
有无保质期 客观事实——包装上印没印、印了多久 shelfLife / shelfUnit 商品本身
是否按效期管理 经营决策——要不要进临期预警、盘点要不要展开到期日 trackExp 客户

两者独立，产生四种组合：

有保质期 按效期管理 典型商品 系统行为
✓ ✓ 鲜牛奶、酸奶、盒装蛋 入库必填生产日期 + 保质期；盘点按到期日展开；参与临期预警
✓ ✗ 卷纸、纸尿裤、洗洁精、盐、糖 生产日期与保质期如实记录备查；不预警、盘点按总数
✗ ✗ 蔬菜、散装肉、鲜活水产、毛巾碗筷 不填效期，只管总数
✗ ✓ — 无意义组合，不出现

纸品这类「有保质期但不影响使用」的商品：保质期照填，trackExp = false。 过期照样能卖，就不该进临期清单、不该让店员按到期日盘点；但数据留着，合规核查或客户改主意时随时可用。

不按效期管理 ≠ 没有生产日期。 生产日期 / 到货日期是客观事实，无论开关如何都照常记录，用于追溯（农残、召回、供应商对账）。开关只控制「是否按效期做经营管理」。

开关的默认值与触发时机（已定）

默认关闭（trackExp = false），系统不做任何推断。 不根据分类、单位、名称去猜这个商品该不该按效期管——猜错的成本远高于让客户多点一下。

时机 行为
新建 / 上架商品 trackExp 默认 false
建档时填了保质期（shelfLife 非空） 自动置为 true（可手动取消）——既然填了保质期，大概率是想管
已建档商品 保持原值，系统从不批量改写
历史 / 种子数据 一律 false，不推断

开启只有三条路径，全是显式动作：

  1. 建档 / 上架时填了保质期 → 自动开（上表第 2 行）
  2. 人工在商品档案改开关
  3. 入库时录入了效期信息 → 提示但不自动开（见下）

入库时录入了生产日期 + 保质期，但开关未开：

数据照常记入批次（pdate / shelfLife 是客观事实必须留痕），但 exp 仍按开关写 9999-12-31。入库单保存后提示：

该商品未启用效期管理，是否开启并按本次信息回填历史批次？　[开启] [暂不]

由人工确认后执行。不自动开启——一次误填就永久改变商品的库存管理模式，代价太大。

待确认：提示是否需要「本次忽略 / 该商品不再提示」两个选项，避免每次入库都弹一次。

开关切换时的数据处理（实现要求）：

  • 关闭 trackExp → 历史批次 exp 刷为 9999-12-31，但 pdate / shelfLife 保留不清空
  • 打开 trackExp → 历史批次按 pdate + shelfLife 批量回填 exp；pdate 缺失的标为待补，不允许留空

二、统一后的数据结构

库存批次表（每笔入库一条）结构不变，只是 exp 永不为 null：

batch = {
  no,                    // 批次号 = 入库单号（仅供退货溯源，店员不关心）
  pdate,                 // 生产日期 / 到货日期：客观事实，无论是否按效期管理都记录（追溯用）
  shelfLife,             // 保质期数值：客观事实，纸品等「有保质期但不影响使用」的也照填
  shelfLifeType,         // 1天 / 2月 / 3年
  exp,                   // 有效期至：'YYYY-MM-DD' 或 '9999-12-31'（永久/不计效期）
  w, s                   // 仓库数量、货架数量
}

盘点行 = GROUP BY (goodsId, exp)

  • 不计效期商品 → 所有批次 exp 都是 9999-12-31 → 天然合并成一行 → 即"盘总数"
  • 计效期商品 → 每个不同到期日一行 → 即"按效期盘"

这两者是同一套代码的自然结果，不需要为"盘总数"写任何分支。

顺带免费解决的三件事

  1. 临期预警不用加过滤条件 —— 9999-12-31 剩余天数恒为天文数字，自动排不进预警清单。
  2. 排序天然正确 —— 按 exp 升序，不计效期永远沉底，临期的排最前先盘。
  3. 盘点粒度不用做开关 —— 一次盘点单里可以混着来：计效期的展开多行，不计效期的一行。

三、存储不分、视图聚合（关键）

批次表在存储层继续保持"每笔入库一条"，只在盘点 / 库存视图按 (商品, 到期日) 聚合。

不要为了减少行数在存储层合并批次，否则会丢掉两个能力：

  • 退货按「原入库批次」结算，需要知道该批次进了多少
  • 退货上限校验 min(该批入库量, 当前批次库存) 需要批次级剩余量

聚合只是展示层的事，溯源信息不丢。

四、五条实现约定（必须钉死）

# 约定 原因
1 永久效期存 '9999-12-31'，不用 null / 空串 空值有三种（null / '' / undefined），分组时会散成三组，是这类设计最经典的 bug。存成真实日期后比较、排序、分组逻辑全部统一
2 存储不分、视图聚合 保住退货按批次结算与批次剩余量校验（见第三节）
3 UI 上讲「不计效期」，不要讲「永久有效」 娃娃菜标"永久有效"店长会觉得系统坏了。语义是"不按到期日管"，不是"不会坏"
4 极短保商品（活鱼 1 天、整鸡 2 天）建议也设成不计效期 当天/隔天清完，按到期日盘没有意义，损耗靠盘点差异修正
5 聚合行的成本取加权平均（商品主档 avgCost），明细可展开看各批次进货价 一行可能含多个批次、不同进价，差异金额需要确定口径

五、两种效期在各环节的行为差异

环节 不计效期（永久） 明确保质期
入库 生产日期 / 保质期可选填（记录备查），不校验 填生产日期 + 保质期，自动算「有效期至」，提交时校验必填
批次 仍按入库单生成批次（溯源用），exp 统一填 9999-12-31 按入库单生成批次，exp = 生产日期 + 保质期
盘点 商品一行，只盘总重量/总数量 商品 × 到期日 逐行盘，按到期日升序（临期在前）
盘点差异 直接调整总库存，记一笔「盘点修正」流水 回写到对应到期日的批次；盘盈且无此到期日 → 新建批次（生产日期 = 到期日 − 保质期反推，成本取最近入库价）；盘盈盘亏不跨日期抵消
销售扣减 扣总数 FIFO，先到期先出
临期预警 不参与（剩余天数恒巨大，自动排除） 参与
损耗管理 靠盘点差异修正（本版唯一手段，日报损单不做） 靠临期下架 + 盘点差异
退货结算 按供应商汇总（入库单号仍可溯源） 按原入库批次结算，退货后该批次库存回退
库存明细页 显示总数变动流水 显示批次维度（入库单号 / 生产日期 / 到期日 / 剩余天数）

关于「不计效期」商品的损耗

不计效期 ≠ 不会损耗。蔬菜、散装货照样会烂、会丢，只是不按到期日管理。

这类商品的库存准确性取决于客户怎么用：

客户选择 库存纠正方式 报损单
盘 正常进盘点单，只盘总数，差异走「盘点修正」自动纠正库存 可选
不盘 损耗没有出口，库存只增不减（日报损单本版不做，见第九节第 2 条） 无解 
库存 = 上期结存 + 进货过磅 − 称重销售 − 盘点差异（日报损单本版不做，暂缺损耗出口）

盘或不盘都由客户决定，系统不做限制。 不计效期只决定"盘的时候不展开到期日"，不决定"能不能盘"。

盘点单的到期日怎么填（交互细则，已定）

原则：系统带出为主，人工新增为辅；新增时下拉优先，手输兜底。

① 系统带出行（占绝大多数）

  • 盘点单生成时按 (商品, exp) 聚合，每行 = 一个到期日，系统数 = 聚合数量
  • 到期日不可编辑 —— 改了就是另一行，等于换了盘点对象；要改只能删掉本行再新增
  • 店员只录「实盘数」

② 新增效期行（库里有但系统没这个到期日 / 盘盈）

  • 入口：盘点明细底部「+ 新增到期日」
  • 到期日控件 下拉优先，候选按此顺序给出： 1. 该商品当前库存中现存的到期日（已在带出行里的排除） 2. 该商品近 90 天入库记录里出现过的到期日 3. 按商品档案默认保质期推算（填了生产日期则自动算 = 生产日期 + 保质期）
  • 下拉里确实没有 → 提供「手动输入」入口，输入时校验：
  • 格式 YYYY-MM-DD
  • 不早于今天 —— 早于今天说明已过期，应走临期处理，不应作为盘盈入库
  • 不计效期商品不显示新增入口 —— 它只有一个 9999-12-31 行，加日期行没有意义

③ 排序与展示

  • 按 exp 升序：临期在前，不计效期永远沉底
  • 剩余天数 = 到期日 − 今天；不计效期行显示 —

④ 提交回写

  • 带出行 → 差异回写该到期日对应的批次（多个批次按到期日升序依次扣）
  • 新增行 → 新建批次，no = 盘点单号，pdate = 到期日 − 保质期（反推），成本取最近入库价
  • 盘盈盘亏不跨到期日抵消

  3. 未开启效期管理但本次录了生产日期 + 保质期 → 保存后弹出「是否开启并按本次信息回填」提示，不自动开启

日报损单：本版不做（见第九节第 2 条，客户使用后再评估）

九、说明与遗留项

1. 盘不盘点由客户决定，不是系统限制（已澄清）

「不计效期」只意味着盘点时不展开到期日（只盘总数），不代表该商品不能进盘点单。

  • 蔬菜、散货与日百在不计效期这件事上没有区别，都按总数盘。
  • 客户想盘就盘（过磅 / 点数录入，走盘点修正），不想盘就不盘。系统不做限制，也不做假设。
  • 因此「蔬菜是否剔出盘点单」不再是产品待决项——它属于客户现场配置。

2. 损耗出口：日报损单本版不做（已决策）

日报损单不纳入本版，等客户实际使用后再评估。

已知影响（接受）： 若客户选择不盘某类不计效期商品，其库存就只有「进货 +」和「销售 −」两个出口，损耗没有出口，库存会长期虚高且不会被纠正。

本版的缓解方式： 引导客户把这类商品纳入盘点——盘点差异本身就能纠正库存，不需要报损单。

后续评估触发条件： 客户反馈"蔬菜库存对不上"或明确表达损耗登记需求时，再启动日报损单。

3. 生鲜日结「理论毛利率」

由「进货 − 销售 − 报损」推算实际毛利率，属进阶形态，未纳入本版。

4. 入库录入效期但未开启开关的提示交互（待确认）

本版定为「提示 + 人工确认，不自动开启」（见第一节）。待确认：提示是否需要「本次忽略 / 该商品不再提示」两个选项，避免同一商品每次入库都弹一次。

4. 客户端角标 / 提醒状态（第3条 · 措辞锁定 A）

角标只出现在加购列表（结算台右侧）；左侧商品区无角标概念。

加购列表对每个加购项（已加购量=N，当前 stock=S）展示：

加购项状态 展示 说明
N > S（缺口>0） 角标「不足{x}」 x = N − S 恒>0；S=0 时 x=N（商品已售罄但已在车里）
N ≤ S 且 S ≤ 5 角标「告急」 库存充足但偏低
N ≤ S 且 S > 5 无角标 充足

左侧商品区（无角标） - stock > 0：可加购，上限=stock；超量弹「库存不足」拦截。 - stock = 0：禁加购，显示「已售罄」状态（纯置灰/文案，非角标，因为加不进结算台）。

关键规则 - 「不足」只能由缺口触发——商品已在加购列表（N≥1）且 N>S。商品区 stock=0 未加购时根本不可能出现「不足」（加不进），那是「已售罄」禁加购状态。 - 不足 与 告急 都是加购列表角标，由「有无缺口」区分：有缺口→不足{x}；无缺口且 S≤5→告急；无缺口且 S>5→无角标。 - 优先级：不足{x}（有缺口）优先于 告急（已在车里且有缺口即不足）。仅两态角标，无第三态。

客户端实现要点 - 维护 stockMap: Map<productId, stock>，SSE inventory.update 到达即更新并触发加购列表重渲染。 - 加购校验：加购时若 已加购量 + 1 > stock → 拦截（「库存不足」）；stock=0 直接禁加购。 - 加购列表项绑定 productId，SSE 推送后无用户操作自动重算角标（缺口→不足{x}）。 - 提交结算：服务端二次校验 stock，不足返回「库存不足{x}」。

5. 管理端消息生命周期（第4条 · 重新上架=不重发，乙锁定）

每条商品两条通知消息（售罄商品必带一条前置的"即将售罄"提醒，同一商品 low 消息早于 sold）。

展示排序（用户 2026-08-26 强调"注意消息顺序"，2026-08-26 三次纠正：消息中心应倒序）：通知中心整体按 ts 严格倒序（最新在上），全局时间单调、无跳跃，符合消息中心惯例。同一商品的「售罄(sold, 时间晚)」显示在上方、「即将售罄(low, 时间早)」显示在下方——low 在其 sold 到达后已自动失效，作为该售罄消息的历史前置提醒保留在下方（关联仍成立，并显示"该商品已售罄，此低库存提醒已失效"说明）。早先"按商品分组、组间倒序"方案（08:30→11:20→10:05→09:12 跳跃）与"整体升序（最旧在上）"方案均已废弃。

消息 触发条件 文案
即将售罄（前置提醒） stock 首次进入 ≤5（含新商品初始即低库存的首次判定） 「库存偏低，请及时补货」（不展示具体剩余量，仅提醒有消息即可）
售罄 stock 首次 = 0 「已售罄」

均为"首次"一次性；区间内波动（如 3↔4）不重复发。

5.1 状态机（服务端为每个商品持久化 notifiedState ∈ {none, low, soldout}）

事件 行为
库存跨越阈值 → ≤5 且 notifiedState≠low：发「库存偏低，请及时补货」，notifiedState=low；→ =0 且 notifiedState≠soldout：发「已售罄」，notifiedState=soldout；→ >5：保持 notifiedState 不变
上架（下架→上架 / 新商品首次上架） 前两条消息置灰（历史过期/已读，不再高亮）；notifiedState 不变
运营标记已读 记录 markedBy（标记人，任何操作员均可标记）；消息状态=已读；不影响 notifiedState
补货处理（库存回升 / 实际入库事件触发） 由【实际入库 / 补货系统事件】驱动（其他功能模块触发，非通知中心人工标记）；记录 handledBy='补货'（固定值，不关联实际人）；消息状态=已处理；不影响 notifiedState
下架 前两条消息置灰冻结 + 停止维护（不再更新、不再发新消息，库存检测对该商品暂停）
重新上架（乙锁定） 不触发任何消息；以重新上架时库存为新基线（重新上架动作本身即便 stock≤5/=0 也不补发）；之后库存从该基线再次真实跨阈值，仍按首次逻辑发
售罄消息到达 → 低库存提醒自动失效（用户 2026-08-26） 同一商品的「即将售罄(low)」提醒在其对应「售罄(sold)」消息已存在且自身仍未读时，自动标记为已失效——不可再标记已读、不可再补货；已读或已处理的 low 不受影响（保留原状态）。语义：商品已售罄，低库存提醒已无意义。通知中心按 失效 = (type==='low' && !read && 同一商品存在 sold) 计算

乙决策理由（用户 2026-08-26）：重新上架即代表运营已重新整理库存，无需再提醒。语义上"重新上架"= 重新观测基线，不重放历史/当前低库存消息，但后续真实下降仍正常通知。

运营操作边界（用户 2026-08-26 补充）：通知中心页面不提供真实的"标记已处理/已补货"操作——「已处理·补货」状态由【实际入库 / 补货系统事件】驱动（其他模块触发）。通知中心仅支持标记已读（记录标记人，任何人可标记）；页面上的"模拟补货"按钮仅用于预览「已处理·补货」效果，非真实业务动作。

已读与已处理是两个独立状态（用户 2026-08-26 补充）：① 点击消息卡片本身不会标记已读，已读只能通过「标记已读」按钮触发；② 已读的消息仍可因补货获得「已处理·补货」标记（补货不覆盖已读/标记人）。状态展示优先级：已下架·冻结 > 已处理·补货 > 已读·{标记人} > 未读。

一、inv-list 库存列表 ↔ Inventorylist（★高，细节差距）

Vue 结构：企业/门店级联 + 分类下拉 + 售品类型 radio(全部/可售/不可售) + 关键词(名称/编码)；列 = 商品名称(链接→批次) / 编码条码 / 规格(称重 kg/l 特殊显示) / 仓库数量 / 货架数量 / 总库存(calc)…；工具栏 4 作业；批次弹窗 fullscreen 含合计行。

demo 现状：售品类型分段(全部/可售/不可售)、分类 9 大类、关键词；列 = 商品名(链接→批次)/编码条码/规格/仓库数量/货架数量/总库存量/总成本价/平均进货价/门店/供应商/状态；工具栏 = 货架补货/退回仓库/整箱拆零/零货装箱 + 批次弹窗(按入库单号分组 FIFO + 合计行)。

差距（升级时按此补）： 1. demo 批次弹窗列为 no/pdate/life/exp/w/s；Vue 有「保质期类型单位」维度（shelfLife + LIFE_TYPES 天/月/年 → 剩余有效期）与 summary 列对齐——建议批次增加 保质期/有效期 体系（跨域：入库单也要有）。 2. demo 4 作业弹窗均有但校验口径为「超仓库/货架存量拦截」；Vue 补货退仓同弹窗按 inType 切文案、数量 blur 校验——基本一致，可保留。 3. demo「商品+批次」来源直接读自身 goods 表（无真实批次主档）；Vue 批次有独立 pkId/batchNo。demo 升级方向：批次对象化。

二、inv-entry 入库单 ↔ Inventoryrecord + Warehouseentry（★中）

Vue 结构：入库单列表(供应商/日期/状态 10红/20绿，已完成禁改删，单号链接详情，批量导入 BatchImport，打印 A4 模板含合计)；编辑为独立页 Warehouseentry（门店含 rkId 锁定、供应商必填、进价 > lastPurchasePrice 标红、生产日期 + 保质期单位 + 保质期至自动算、称重 3 位小数其余整数、保存=待提交、入库完成=commit 校验未填进价确认）。

demo 现状：列表 + 大弹窗编辑合一；列/状态机(10橙→20绿)/新增编辑提交/选商品均有；编号 RK+日期+3 位随机；提交后 warehouse+qty、batches.unshift({no,pdate,life:'待定',exp:'—'})。

差距（升级优先级：高）： 1. 生产日期/保质期/有效期字段缺失——demo batches 里 life/exp 写死「待定/—」，入库单明细没有 pdate/life 录入与计算。Vue 已完整实现（LIFE_TYPES + 自动算保质期至）。库存升级核心短板。 2. 进价无「高于最近采购价标红」提醒。 3. 无打印（A4 入库单模板）。 4. 无真实批量导入（BatchImport 三步骤：上传→按供应商拆单→逐单保存）；demo 导入为简化弹窗。 5. 完成态约束弱：Vue 已完成禁改/禁删，demo 需核实行内是否全禁（入库日期/门店硬编码 2026-09-03/S2001 需动态化）。

三、inv-transfer 调拨 ↔ Stockinorout + Inoroutrecord（★低，上游不可用）

Vue 现状（客观说明）：Stockinorout「调货」为半成品——调的是盘点接口 pkPreCommit/pkCommit/pkDetail，字段/列与调拨错位、返回误跳退货记录；Inoroutrecord「调拨记录」未接后端，发货/编辑/取消均为占位。即 Vue 侧调拨实际不可运行。

demo 现状：列表(四态 pending/shipped/done/cancel + 行内流转按钮) + 新增弹窗(店间调拨/仓库补货/门店退货至仓 + 金额=qty×avgCost 即时算)，独立可用。

差距与结论： 1. 状态口径不一致：Vue 记录页为 0已确认/1待确认/2已取消 三态（且与调货业务描述不匹配）；demo 为四态单据流。因上游不可用，建议 demo 保留自洽模型，升级前与产品确认目标状态机（本次升级建议一并定稿）。 2. demo 发货/完成不真实扣减/增加库存（仅演示单）——升级必须接通 tcm_inv_goods_v1 双门店增减 + 批次归属。 3. fromStore 固定 S2001、申请类型与调入方来源简化。

四、inv-return 退货 ↔ Returnedrecord + Returnedgoods（★中）

Vue 结构：退货单以已完成入库单的批次行为来源（选品弹窗带「入库单号 rkNo」筛选），明细含入库单号/批次/进货数量/当前库存；最大退货量 = min(入库数量, 当前库存)；退货价 ≤ 进货价；称重 3 位小数；整件未填数量 thCommit 时确认忽略；状态红/绿；打印。

demo 现状：来源 = 最早入库批次(FIFO) 取 batches[0]，可退库存=qty；数量/退货价自由输入、金额联动；原因下拉(品质/临期/破损/多送/其他)；提交回退库存 Max(0, warehouse−qty)、batches[0].w 扣减。

差距（升级优先级：中高）： 1. 可退上限校验缺失：demo 未做 min(入库数量, 当前库存) 上限，仅库存字段展示。 2. 退货价 ≤ 进货价 未校验。 3. 来源选择粒度粗：FIFO 仅取首批次，无「按已完成入库单选批次」入口（Vue 用 addGoods + rkNo 筛选）。 4. 无打印。

五、inv-check 盘点 ↔ Stocktakerecord + Stocktake + Inventrysnapshot（★低）

Vue 结构：盘点方式 = 动态(0)/锁库(1)；区域 = 货架/仓库（影响快照与理论库存口径）；同商品合并 + 批次可选增行；锁库显示库存、动态显示 快照 + 变动汇总(货架补货/退仓/销售/售后) → 理论库存 = 快照 + 变动；差异量 = 理论库存 − 实盘；差异金额 = 差异量 × 单位成本（非 0 标红）；60s 批次刷新；快照独立页回看；完成后禁改。

demo 现状：方式 = 全盘/抽盘（与 Vue 语义不同）；区域 select(全店等)；账面 = warehouse+shelf 快照；实盘 input；差异 oninput 即时算；diffAmt 恒 0（金额未接入）；保存即完成；「按账面完成」会把盘点中单置 0 差异。

差距（升级优先级：高，口径要重对齐）： 1. 盘点方式语义错误：demo「全盘/抽盘」非 Vue「动态/锁库」——需重定义（动态=含销售等变动汇总；锁库=冻结时点）。这是口径级问题，升级必须先定。 2. 无理论库存/变动汇总维度（货架补货/退仓/销售/售后 4 类变动来源 demo 无模型）。 3. 差异金额未接入（demo diffAmt=0）。 4. 无批次级盘点、无快照独立页、无 60s 刷新（demo 内嵌快照统计弹窗可作基础）。

7. 接口通用规范（统一约定）

本章节为全模块统一约定，所有接口（含复用与新增）均遵守。规范取自现有 /mnmart 接口体系。

  • 基础路径：/mnmart。
  • 协议 / 编码：HTTPS，Content-Type: application/json，字符 UTF-8。
  • 请求方法：统一 POST（列表、查询、详情、写操作均用 POST，与现有体系一致）。
  • 鉴权：POST /mnmart/user/login 登录后返回 jwtToken；后续请求在 Header 携带 Authorization: Bearer {jwtToken}（与现有 /mnmart 接口鉴权一致；具体 header 名以网关为准，统一走 JWT）。
  • 请求包体（统一）： json { "data": { "...业务参数..." }, "requestPage": { "currentPage": 1, "pageSize": 10 } }
  • 列表/分页接口带 requestPage；单条查询/写操作可省略 requestPage。
  • 通用上下文：几乎所有接口需携带 companyId、shopId（租户 + 门店隔离）；shopId 缺省表示跨门店/总部视角。
  • 响应包体（统一）： json { "code": 0, "message": "success", "data": [ "...或对象..." ], "pageInfo": { "pageSize": 10, "currentPage": 1, "totalPages": 1, "totalRecord": 1 } }
  • 列表接口：data 为数组，pageInfo 返回分页信息（pageSize/currentPage/totalPages/totalRecord）。
  • 单条/对象接口：data 为对象，无 pageInfo。
  • 成功判定：以 code === 0 为准；message 为提示文案（现有体系成功时可能为 "success" 或具体成功文案，仅作展示，不应用于逻辑分支）。
  • 字段命名：小驼峰（camelCase），与现有 goods*、shop*、batch* 等保持一致。
  • 时间格式：yyyy-MM-dd HH:mm:ss（字符串）；纯日期 yyyy-MM-dd。
  • 金额：decimal（元，两位小数），JSON 数字（如 3.99）。

10. 错误码约定

  • 与现有 /mnmart 体系一致：code === 0 成功；code ≠ 0 为业务/系统错误，message 带回可读文案（前端直接提示 message）。

  • 建议业务码分段（与现有风格对齐，非强制）：1xxx 参数类、2xxx 业务校验类、5xxx 服务端异常。示例：
code 含义 处理建议
0 成功 —
（业务码） 计划不存在 提示并刷新列表
（业务码） 商品/条码不存在 提示商品无效
（业务码） 商品已在计划（手动场景） 提示或自动定位

1. 背景与目标

价签打印是门店日常高频操作。当前改价、上新、补货均需重新打印价签，但缺乏"批量组织 + 按计划打印"的能力，操作员常逐张打印、易漏打、易与旧价签混淆（货签价不符存在合规风险）。

目标：提供"打印计划"管理能力，支持把待打印商品按门店/类型组织成计划，统一预览价签并批量打印；调价场景自动归集到当天计划，确保价签及时、准确更新。

2. 用户与场景

角色 职责
店长 / 运营 创建打印计划、查看计划状态、安排打印、核对价签准确性
收银 / 理货员 按计划加入/移除商品、设置打印份数、执行打印

典型场景 1. 每日巡检发现需换签 → 手动新建计划，加入商品，批量打印。 2. 后台改价（服务端事件）→ 商品由服务端自动归集进入当天"调价"计划，计划内比对价格，旧已打印价签自动重置为待打印。用户无操作。 3. 用户在「改价日志」页开启「自动加入调价打印计划」开关 → 商品信息变更（名称/价格/会员价/产地等）自动归集进当天调价计划；开关关闭则完全不自动加入（§4.7）。用户侧自动触发。

4.5 价签打印

架构说明：打印为客户端行为——客户端直接基于计划项字段本地渲染价签并完成物理打印输出；服务端不执行打印，仅接收客户端上报的打印动作并持久化记录。价签打印与称重打码（code/printCode 系列）是不同功能，本模块不依赖称重打码接口。

交互流程： 1. 详情点「打印选中」→ 客户端弹出价签预览：可选价签模板（标准价签 / 促销价签等），直接使用计划项字段（商品名称、价格、原价、会员价、条码、规格、生产日期等）在客户端渲染价签。 2. 客户端本地执行物理打印（如浏览器 window.print() 或客户端打印通道），按每项 printQty 循环生成对应张数。 3. 打印完成后，客户端调用 POST /mnmart/printPlan/print（详见《接口定义》§9.8）通知服务端记录本次打印（打印项、份数、模板、时间、操作人）。服务端仅落盘打印记录，不执行打印。 4. 已打印商品可手动勾选进行二次打印（旧价签作废场景），打印后同样上报记录。

打印份数：每项按 printQty 循环打印；上报记录成功后该项 printed=true、printedAt=当前时间。

价签打印为纯客户端渲染 + 输出，所需字段均来自计划项（详见《接口定义》§6.5 PlanItem），无需服务端打码接口；服务端仅通过 printPlan/print 记录打印动作。

4.6 调价自动入计划（服务端驱动，用户无操作）

定位：本能力由服务端完成，前端无入口、用户无感知。与 §4.7「改价日志自动加入」（用户侧开关触发）是两类独立能力，勿混淆；现调价归集仅由本能力（服务端自动）与规则5 引擎（§5.5）承担。

触发方：后台改价、总部调价下发等商品价格变更事件完成时，由服务端自动执行归集。

交互流程（服务端）： 1. 服务端接收到商品改价事件（携带 shopId/companyId/最新 goodsPrice/goodsListPrice/vipPrice）。 2. 调用内部归集接口 POST /mnmart/printPlan/autoAddFromPriceChange（详见《接口定义》§9.9，仅服务端调用，前端不可见）。 3. 执行 §5.3 调价归集逻辑（三层决策树）：按「当天调价自动计划 → 当天未完成计划 → 新建调价自动计划」选定目标计划，再对商品做价格比对（同价不重复、异价更新并视情况重置已打印）。 4. 前端仅在「打印计划」列表/详情中被动看到结果（计划出现或商品更新）。

说明：当前 MVP（最小可行产品）采用前端内置浏览器端 Mock（无真实服务端），故该能力未实际触发；对接后端后由后端实现。详见《接口定义》§14 接口 Mock 说明。

4.7 改价日志 · 自动加入调价打印计划（开关）

✅ v1.7 调整：由 v1.5 的「勾选 + 加入按钮」改为开关（toggle）模式。开关打开后，商品信息变更自动加入调价打印计划；开关关闭后，商品信息变更不会自动加入。与服务端自动归集（§4.6）/规则5 引擎（§5.5）并行不悖。

定位：「改价日志」页提供全局开关「自动加入调价打印计划」，控制商品信息变更是否自动归集到调价打印计划。属于用户侧自动触发机制，区别于 §4.6 的服务端事件触发。

开关语义： - 开关打开（ON）：当商品发生以下信息变更时，系统自动将商品归集进当天「调价自动」计划（price-change）： - 商品名称变更； - 价格变更：现价（price / 改后价）、原价（origPrice）； - 其他扩展字段变更：会员价（memberPrice）、产地（origin）等（监控字段可扩展，见前端 PP_AUTO_FIELDS）。 - 入计划遵循 §5.3 P1→P2→P3 三层决策树；同条码商品按价格比对，异价更新并重置已打印（规则2/4）。 - 开关关闭（OFF）：商品信息变更不会自动加入任何打印计划（仍可在日志页手动勾选「加入选中项」显式加入）。

交互流程： 1. 操作栏提供开关「自动加入调价打印计划」（状态持久化于 localStorage，默认关闭）+ 状态指示 + 按钮「模拟新改价」（演示用，模拟一次商品信息变更）+ 按钮「加入选中项」（手动，始终加入调价自动计划）。 2. 开关打开后：进入页面时静默同步（确保已变更商品已在计划中）；之后每次商品信息变更（含点击「模拟新改价」）即自动归集，并轻提示「已自动加入调价打印计划」；如开关关闭则仅记录变更、不加入。 3. 开关状态变化即时生效并持久化；打开时立即对当前全部已变更商品执行一次归集。

前置条件：进入「改价日志」页（独立页面），可按门店、日期筛选当日改价记录。

数据来源：复用 POST /mnmart/goods/listGoodsPriceRecord（详见《接口定义》§8），入参 data.companyId/data.shopId/data.startTime/data.endTime/data.keyword + requestPage，返回改价记录（goodsId/goodsName/goodsCode/goodsSpec/goodsUnitName/goodsListPrice 原价/goodsPrice 改前价/goodsAfterPrice 改后价/operator/recordTime）。

5. 业务规则

5.1 生产日期（FIFO）

  • 商品存在多批次时，价签生产日期取最早批次（最临近过期）。
  • 多批次共存时，详情表格生产日期旁标注批次数（如「3批」），hover 提示规则。
  • 批次数据来源：POST /mnmart/printPlan/addGoods 响应中随计划项一并返回（详见《接口定义》§9.6，含 produceDate/batchCount/batches）；FIFO 取最早 produceDate，批次数 = batchCount（= batches 数组长度）。原独立批次查询接口 POST /mnmart/inventory/batchListByGoodsIdCode（详见《接口定义》§8）兼容保留，但打印计划场景不再单独调用，避免冗余请求（需求2）。

5.2 计划状态

空计划(无商品) ──► 待打印(pending)
存在未打印商品 ──► 部分打印(partial)
全部商品已打印 ──► 已完成(done)
  • 计划无商品 → 待打印(pending)
  • 存在未打印商品 → 部分打印(partial)
  • 全部商品已打印 → 已完成(done)

5.3 调价归集逻辑（三层决策树，两端共用）

本逻辑为「调价归集」的共用业务规则，被两类触发方复用： - A. 服务端自动入计划（§4.6）：后端改价事件自动调用 autoAddFromPriceChange，或销售改价 / 商品编辑等永久调价行为触发（§5.5）。 - B. 调价归集引擎（规则5 统一入口）：前端 ppAddPriceChangeProducts(products)（index.html）提供，供销售改价 / 商品编辑等永久调价行为调用（§5.5），亦被 §4.7 开关自动触发复用。 触发方不同，但归集、价格比对与状态重置规则一致。字段以现有商品体系为准：price(售价) / origPrice(原价) / memberPrice(会员价)。

第一层：选定目标计划（按优先级） 1. P1（规则4） 当天已存在「调价自动」计划（type=price-change，无论待打印 / 部分打印 / 已完成）→ 直接作为目标计划。 2. P2（规则2） 否则，当天存在未完成计划（status≠done，即待打印 / 部分打印）→ 以该未完成计划为目标。 3. P3（规则3） 否则（当天仅有已完成计划，或当天无任何计划）→ 新建「调价自动」计划（type=price-change），作为目标。

说明：P1 优先于 P2 / P3，确保「调价自动计划」是调价商品的统一归集入口；仅当当天无调价自动计划时，才退而用未完成计划或新建。

第二层：商品加入 / 更新（目标计划内） - 计划中无同条码商品 → 新增（待打印，写入最新价）。 - 计划中有同条码商品，且价格（售价 / 原价 / 会员价）完全相同 → 不重复加入、不修改任何信息（含打印状态）（对应规则1：价格没变则不更新、不重置）。 - 计划中有同条码商品，且价格不同 → 是否更新取决于目标计划类型与状态（二者共同前提均为「价格变更且与计划中价格不同」）： - 目标计划为「调价自动」（type=price-change，无论是否完成）→ 更新商品信息（最新价）并重置为待打印（旧价签作废，需重打）。 - 目标计划为「用户新增」（type=manual）且计划未完成（status≠done，以计划状态为准，非商品状态）→ 更新商品信息并重置为待打印。 - 目标计划为「用户新增」且计划已完成（status=done）→ 即便价格不同，也不更新信息、不重置打印状态。

说明：规则1「已打印数据不进行更新」与规则2 / 4「已打印项更新价格并标记待打印」的张力，已由本规则消解——价格相同则任何信息都不动（规则1）；价格不同则仅当目标计划为「调价自动」或「用户新增且未完成」时才更新信息并重置待打印（规则2 / 4），用户新增且已完成的计划即便价格不同也保持原状。该判定以「防止打印过期价格」为总目标，且以计划状态（而非商品打印状态）作为用户新增计划的判定依据。

5.4 打印份数

  • 每项默认 1 份；未打印项可调增减（下限 1）；已打印项显示份数、不可调。
  • 打印时按 printQty 循环生成价签。

5.5 调价行为定义（规则5）

所有永久性价格调整行为，均视为调价行为，相关商品须归集进入打印计划（经 §5.3 三层决策树），以确保价签与最新售价一致： - 后台改价 / 总部调价下发（服务端事件，§4.6）。 - 销售改价：前台销售环节发生的价格变更。 - 商品编辑：商品主数据维护中修改了 price / origPrice / memberPrice。 - 其他导致商品售价永久变化的操作（以产品定义为准）。

判定标准：是否写回商品主数据售价。仅当价格变更持久化到商品主数据时才计入；临时挂牌、未落库的价格试算不在此列。

5.6 打印进度计数（规则6）

  • 计划打印进度 = 已打印商品数 / 总商品数（与 §5.2 状态联动：pendingCount = totalCount - printedCount）。
  • 商品状态翻转时计数同步变化：
  • 待打印 → 已打印：该计划 printedCount +1（进度 +1）。
  • 已打印 → 待打印（如 §5.3 价格变动重置）：printedCount -1（进度 -1）。
  • 计数由打印 / 重置动作触发即时重算，不依赖异步对账。

13. 名词解释

  • 原价（origPrice）：商品吊牌/指导价，价签上以普通文本展示（非划线）。
  • FIFO：先进先出，此处指按批次生产日期（produceDate）取最早批次。
  • 二次打印：已打印商品因调价/破损需重打，手动勾选后重新出签。
  • 调价自动入计划：服务端在商品改价完成时自动归集到当天最新调价计划，用户无操作（见 §4.6 / 《接口定义》§9.9）。
  • 改价日志自动加入：「改价日志」页开关开启后，商品信息变更自动归集进调价计划；关闭则不自动加入（见 §4.7 / 《接口定义》§9.10）。
  • 调价自动计划：由 §4.6 服务端自动归集、类型 type=price-change 的计划。

9.4 文件下载 POST /mnmart/fileStore/download

核心定位：用户获取文件内容的唯一途径。本模块无在线预览，所有内容获取通过本接口完成（见需求 §4.3）。

请求 data：{ "fileId": "fs-20260728-0001" }

响应（两种模式，由后端决定）： - 模式 A（推荐，下载地址）：data 返回带签名的临时 downloadUrl + fileName + fileSize；前端以 <a download> 触发浏览器下载，不直接暴露存储路径。 json { "code": 0, "message": "success", "data": { "fileId": "fs-20260728-0001", "fileName": "崧泽店价签模板_v3.png", "downloadUrl": "https://cdn.xxx.com/fs/...?sign=xxx&exp=3600", "expireIn": 3600 } } - 模式 B（流式）：接口直接返回文件二进制流（Content-Type 为文件 MIME，Content-Disposition: attachment; filename=...），前端以 Blob 落盘。此时 data 为空对象。

downloadUrl 须带时效签名（如 exp/sign），防盗链/防篡改；过期需重新调本接口换取。

可选回调 POST /mnmart/fileStore/download/record（不影响下载本身）：记录下载行为（审计/统计），data 携带 fileId/operatorId/downloadAt。

9.5 文件删除 POST /mnmart/fileStore/delete

或

{ "fileIds": ["fs-...","fs-..."] }

业务说明：物理删除策略（软删/硬删）由后端决定；权限（谁可删）由后端控制，前端仅负责二次确认与刷新。 响应 data：null（以 code === 0 判定成功）。

  • 与现有 /mnmart 体系一致：code === 0 成功；code ≠ 0 为业务/系统错误，message 带回可读文案（前端直接提示 message）。
  • 建议业务码分段（与现有风格对齐，非强制）：1xxx 参数类、2xxx 业务校验类、5xxx 服务端异常。示例：

1. 背景与目标

面向美天各市场内部，支撑台账管理、文件归档与数据备份（价签稿、装修图、活动海报、培训资料、制度文档、对账表、供应商资质等）。

  • 不涉及上级对下级的文件下发/传达，无上级文件库、无跨层级推送。
  • 文件归属与使用限定在单一市场内。
  • 不提供在线预览：内容仅通过"下载到本地"获取（区别于网盘，简化架构）。

2. 用户与场景

所有角色均限所属单一市场内操作，无跨市场角色。

角色 职责（限本市场内）
市场运营 / 档案管理员 上传维护本市场文件
市场店长 浏览下载本市场文件、维护台账
市场收银 / 理货员 下载本市场操作指引、价签样例

典型场景：市场运营上传价签稿（归属本市场）→ 本市场用户下载，其他市场不可见；A、B 市场文件库各自独立，互不可见、不可共享。

3. 功能概览

4. 详细功能需求

4.0 市场隔离（核心约束）

  • 单选查询：市场选择器仅可选一个市场；无"全部市场"聚合视图，文件不跨市场混合查阅。
  • 单市场视图：同时仅展示当前市场文件，列表/搜索均限该市场。
  • 上传限定市场层级：文件归属 = 当前市场（系统带入，不可选其他市场）。
  • 不互通不共享：无跨市场共享/转发/复制/下发入口；无跨市场检索与聚合。
  • 权限：用户仅能访问所属市场文件库（marketId 鉴权，见接口 §7/§10）。

4.1 文件库浏览

进入「文件库」页面（集成于淘菜猫 SaaS，沿用现有 enterprise 角色与 UI 规范）。

  1. 加载列表 POST /mnmart/fileStore/list（限当前市场）。
  2. 顶部筛选栏：市场选择器（最左，单选）→ 任务类型下拉 → 关键字搜索 →「需求说明」按钮。
  3. 列表列：复选、序号、文件名、文件类型、任务类型、大小、最后操作人、最后操作时间、操作（下载/删除）。
  4. 「下载」触发浏览器下载（不预览）；「删除」二次确认；支持分页。
  5. 空态：当前市场无文件 / 搜索无结果分别提示。
  6. 顶部展示当前市场存储用量（仅统计已用空间，不限额），按市场隔离；随上传 / 删除动态刷新。

4.2 文件上传

  1. 选文件（单文件），展示待传信息。
  2. 填归属：任务类型（选填，默认其他）。
  3. 归属市场只读 = 当前市场。
  4. 提交 POST /mnmart/fileStore/upload（multipart/form-data，marketId 必传）；同名策略由 overwrite 决定。
  5. 成功后列表刷新、新文件置顶（仅当前市场可见）。

限制（前端提示，后端强制）：单个文件 < 20MB，不支持批量提交；拦截可执行/脚本类（.exe/.bat/.sh/.js 等）。

4.3 文件下载

下载是获取内容的唯一途径，无预览、无内嵌查看器。列表「下载」或批量下载 → POST /mnmart/fileStore/download → 返回 downloadUrl（签名时效）或二进制流 → 浏览器落盘。

4.5 任务类型

  • 受控枚举：巡检/验收/整改/培训/盘点/快检抽检/索证索票/其他（可由管理端维护），用于标记文件业务属性。
  • 仅元数据，非任务管理系统（无派单/进度）。
  • 上传时选填，浏览时按 taskType 过滤，列表展示该列。

4.7 删除

  • 删除前强制提醒（不可逆）：点击「删除」弹出确认框，醒目标注「文件删除后将无法找回」，并提示「建议删除前先下载备份到本地」。
  • 提供「先去下载」入口（关闭确认框并触发下载），确认删除为红色危险操作。
  • 删除 → POST /mnmart/fileStore/delete（物理删除策略软/硬删由后端决定，前端仅负责二次确认与刷新）。

4.8 删除记录（审计留痕）

文件删除后不可找回，为便于文件丢失时确认责任、追溯删除人，系统对每次删除留存审计记录（仅元数据，不含文件内容）。

  • 记录时机：删除成功即写入一条记录，保留删除这一最后节点，并附带被删文件的「最后操作人 / 最后操作时间」（= 文件库列表同名字段，更新优先于上传）——即文件最后经手人，便于文件丢失时向其确认本地是否仍存原件。其余字段：文件名、文件类型、任务类型、大小、归属市场、删除人（当前操作人）、删除时间。不逐一拆分上传/更新等中间节点——文件生命周期的人员与时间在「文件库列表」以「最后操作人 / 最后操作时间」统一呈现，删除记录只额外补充「谁删的」。
  • 查看入口：文件库操作栏「🗑 删除记录」按钮，弹窗按删除时间倒序展示（最新在前）。
  • 用途边界：仅用于责任追溯，不等于回收站——记录不可恢复文件，仅证明「谁在何时删了什么」。
  • 接口：POST /mnmart/fileStore/deleteLog（按 marketId 查询该市场删除记录，见《接口定义》§9.7）。

5. 业务规则

5.1 去重

fileId 唯一；同名由覆盖策略处理。

5.2 类型映射

fileType 含义 扩展名
image 图片 jpg/jpeg/png/gif/webp/bmp
doc 文档 pdf/doc/docx
sheet 表格 xls/xlsx/csv
ppt 演示文稿 ppt/pptx
text 文本 txt/md/log
archive 压缩包 zip/rar/7z/tar/gz
video 视频 mp4/avi/mov
audio 音频 mp3/wav
other 其他 其余
  • 文件类型由前端按扩展名自动识别，用户无需选择；列表"文件类型"列展示图标 + 中文名。
  • 文档类（doc/ppt/text 等）均不提供预览，仅可下载。

5.3 同名策略

同名再传，后端按 overwrite：覆盖（更新 version）/ 新增版本（保留旧版）/ 拒绝（报错提示）。

5.4 大小

字节存储，展示 B/KB/MB/GB（1024 进制，1 位小数）。

5.5 持续更新

同类文件多次上传以"最新版优先、旧版可选回溯"支持迭代，避免 xxx_v2_final 式命名。

一、需求

超市采购策略：先定价，再入库。

  1. 与供应商先协定价格，形成「定价（协议价）」
  2. 供应商送货时，门店按送货单录入实际进货价
  3. 送货价与定价一致才允许入库——防止供应商擅自加价
  4. 价格不一致时，需由公司采购经理修改定价，先定后入
  5. 顺带管控：防止进货价修改后商品售价未及时调整

二、现状摸排（实测 shared/ms-inventory.js）

维度 现状 缺口
入库价格 invEntryPriceCell 自由输入 无硬约束
价格校验 仅 above = it.price > last，输入框变红+一句"高于最近采购价" 软提示，不阻断
定价实体 无——没有"供应商 × 商品"的协议价 核心缺失
入库状态 10 待提交 / 20 已完成 无异常态、无审批
供应商档案 名称、地址、联系人、电话 无价格字段

核心结论： 整套"定价—送货价—售价"三件套的实体都缺，必须新建。现有"高于最近采购价"软提示可以删掉——它既不可信（最近价 ≠ 协议价）又不可控。

三、结论：新增六个对象 + 一个门店级模块

  1. 门店成本控制（cost_control）——门店级配置，两个开关 + 子规则，由客户在「门店管理 → 管控配置 → 进价管控」里设置（第四节）
  2. 采购定价（supply_price）——门店级（scope='store'，storeId 必填），供应商 × 商品编码 × 协议价，长期有效 + 调价记录；集团层字段预留（scope='group'，本期不建数据）
  3. 商品别名（goods_alias）——门店 × 商品编码 × 本店叫法，解决名称差异（只影响显示，不影响定价）
  4. 调价单（price_change）——调价走审批，审批时强制检查售价联动
  5. 价格异常知会（price_notice）——低价场景不阻断收货，但必须回到采购经理手里闭环
  6. 入库单扩展字段——价格校验结果快照（priceCheck）+ 状态机新增 15 价格异常 / 25 待入库审核 / 30 已拒收

4.1 开关 1：统一定价

开启后，本门店入库按以下规则校验（配置一次，长期生效；每个门店可独立设）：

子规则 取值 默认
未定价商品是否允许入库 允许 / 禁止 / 审核后入库 禁止
高价商品处理规则 禁止入库 / 审核后入库 禁止入库
低价商品处理规则 禁止入库 / 仅入库（不修改采购报价） / 审核后入库 仅入库（不修改采购报价）

三个选项的语义细节：

  • 禁止入库：校验不通过，单据停在 15 价格异常，库存不变。这是需求核心：供应商加价绝不入库。
  • 不给"议价入库"开后门（09-08 与用户确认）：门店配成禁止，说明它有自己的管理制度，系统就严格执行。硬塞后门等于替客户破坏它自己定的规矩。
  • 审核后入库：单据停在 15 价格异常，采购经理审批通过后入库。现场议价、送错规格这类场景就在这里解决——见下方「审批人的三个动作」。未定价配「审核后入库」适用于：新商品来不及定价、货已到店——审一下、顺手把价定了，库存和成本两不耽误。
  • 仅入库（不修改采购报价）：低价时货照收、库存增加，定价表不动。但差异必须留痕（记入价格波动台账），不生成待处理知会——这是客户主动选择的"不纠偏"。注意： 选了这项意味着客户接受"这批便宜了"是临时/偶发的，不进定价体系。

系统规则优先于人工（09-10 落地，09-11 前移到提交端）：命中「禁止入库」规则的入库单（含未定价禁入）在提交时即被拦截——单据留在「待提交」，提交时点名提示命中商品与原因，提交人先维护定价或调整商品后再提交；注定不能批的单不再进入审批队列。审批页的重算守卫保留为兜底（场景：提交后定价被删除或规则改严），改价后仍命中 forbid 依然不放行。审批人只能在规则允许的范围内决定。

一单多商品按行独立判定（09-10）：一次入库是一车货，异常往往不止一个商品。整单校验对每个商品行独立出结论——forbid 行拦整单（提示只点名 forbid 行，不误伤 audit 行）、audit 行可批、entry_only 行照常入库并记知会、合规行无感。单据只要存在任一 block 就进 15 价格异常；「仅本次改价」把 forbid/audit 行改到位后重算通过即可整单放行，此时新产生的低价差异会补记知会（同单同商品同价不重复）。定价按「商品+门店+供应商」隔离查价——单内商品必须都是该供应商体系，跨供应商的商品会判「未定价」，所以采购单天然按供应商分开建单。

审批人的三个动作（议价能力在这里，不是第三个配置项）

「审核后入库」模式下，采购经理在审批界面可以做一个动作集合，"按议定中间价入库"是其中之一，不需要单独配一个规则：

动作 效果 适用场景
按入库价批准（原「批准原样」，09-11 更名） 按单据入库价（送货价）整单入库；默认定价表不动，可选勾选「同步更新定价」把入库价写入当前段 价格确实合理只是需要人确认；供应商确已调价、按新价正常收货时勾选同步，下次同价进货不再拦截
改价后入库（仅本次） 审批人直接改本次入库价，入库存、记成本；默认定价表不动，可选勾选「同步更新定价」把改后价写入当前段 送错规格、按错档送，双方现场议定按中间价收，下次仍按原定价校验；供应商确已调价时勾选同步
驳回 单据回到 10 待提交，可改后重提或拒收 不接受这个价

关键是"仅本次"与"同步更新定价"要分开：两条批准路径默认都只影响这一笔；如果供应商是真的涨价了，常规路径应当另走调价单更新定价表（第六节），而不是在审批里偷偷改基准。同步更新定价必须显式勾选（默认不勾），让用户看得见区别，否则定价表会被一次次"仅本次"架空。09-11 起「按入库价批准」也提供同款勾选项——供应商确已调价、按新价正常收货时，批准 + 同步一步完成，避免下一张同价单再被拦一次。

审批动作一律二次确认（09-11 落地）：批准 / 驳回 / 拒收都是单据级、不可撤销的状态流转，点击后立即重算并落库，因此每一个动作都先弹确认，且确认框里写清后果，不做"点一下就走"：

动作 确认框给出的信息
按入库价批准 先弹小窗：逐行列「定价 vs 入库价 + 对比」+「同步更新定价」勾选项；点「下一步」后再出一次确认（门店、供应商、商品项数、批准后合计金额，并声明"整单立即计入库存，不可撤销"）
仅本次改价入库 弹窗内实时显示「原件合计 → 改后合计 + 已修改项数」+「同步更新定价」勾选项；点「确认入库」后再出一次确认，逐条列出改动（如 娃娃菜 ¥3.20 → ¥2.80）+ 合计；勾选同步时写明「同时更新采购定价 N 项」及跳过项
驳回 声明"退回待提交，库存不变，提交人可修改后重提"
拒收 声明"拒收为终态：库存不会增加，单据保留供对账，之后不能再审批"

两点实现口径：

  • 规则优先于确认：二次确认放在整单校验之后。若本单仍命中「禁止入库」规则，先弹 toast 拦截、不弹确认框——避免用户确认半天最后被规则挡回。校验用"影子单"预演（把本次改价套到副本上算），取消确认时原单的价格、金额、知会零污染。
  • 详情页的"提交入库"同样确认，且确认文案随校验结果变化：合规→"提交后整单立即计入库存"；开着入库审核→"需审核通过才计入库存"；价格异常→"库存不会增加，将置为价格异常待审批"。

审批队列构成、四动作口径、二次确认的完整需求见《价格审批模块需求说明》；本节只保留与管控规则相关的结论。

因此"按议定中间价入库"不作为一个独立的入库处理规则——它本质是审核动作，依赖审核通道存在；没有审核通道时它无从执行，而门店若配成"禁止"，本就是自己的制度选择。

4.1.1 价格提醒是硬性的，与处理规则正交（必做，不可配置关闭）

凡是开启了统一定价的门店，只要价格不一致，就必须提醒——不管处理规则配成"禁止入库"还是"仅入库"。

提醒 ≠ 处理，两件事必须分开：

是什么 能否配置关闭
提醒 让人知道价格有波动 不能——开启统一定价就必须提醒
处理 让人决定这批货怎么走 能——禁止 / 仅入库 / 审核后入库

我上一版把"仅入库（不修改采购报价）"处理成"只记台账、不打扰人"——这是错的。客户选"仅入库"只代表不去改定价，不代表不想知道。

提醒落在四个位置，缺一不可：

位置 展示内容
① 录入时（实时） 价格输入框旁显示「定价 ¥2.80（+¥0.30 / +12%）」，高价标红、低价标黄；不用提交才知道
② 入库单详情 逐行展开：定价 / 送货价 / 差异额 / 差异率 / 波动标记（↑↓），异常行置顶
③ 入库单列表 新增「价格波动」列，直接显示 ↑12% / ↓5%，颜色区分——不用点进详情就能看到哪单有问题
④ 价格波动台账（报表） 按供应商 / 商品 / 门店 / 时间段查历史波动，可导出；用于供应商谈判与内审

为什么列表上也要有： 采购经理每天看的是列表，不是逐单详情。差异只藏在详情里等于没人看——这就是"防止供应商加价"最容易失效的地方。

4.2 开关 2：入库审核

开启后，所有入库数据均需审核确认后才入库（不论价格是否匹配）。

审核人（2026-09-08 用户定）： 入库审核只配开关，不配审核人——谁能审由角色权限决定，在「系统管理 → 角色管理 → 权限配置」里勾。UI 上只写这一句路径，不展开论证。

demo 现状（实现提示）： 当前授权是菜单级（有页面权限即可操作），还没有独立的"审核"操作权限点——即"能进价格审批页"＝"能审"。正式版建议拆出 audit 权限点，把"能看"和"能审"分开（与 T7 采购经理角色一并做）。

4.2.1 两个「审核」是独立的，别混为一谈

配置里会出现两处带"审核"字样的东西，它们互不影响：

触发条件 由谁控制 关闭后
价格异常审核 仅价格不匹配的异常单 统一定价开关下的 highAction / lowAction 配成「禁止入库」才拦；配成「仅入库」则直接放行
入库审核（4.2 开关） 所有入库单，不论价格 入库审核开关 该开关关闭不影响价格校验——价格照校，异常照拦

所以：关掉「入库审核」开关 ≠ 高价规则失效。 高价单照样进 15 价格异常等采购经理审，只有把 highAction 配成「禁止入库」才是真的禁止。

反过来也成立：开着「入库审核」开关，highAction = 禁止入库 的单依然被系统直接拦下，不会因为有人工审核就放行——系统规则优先于人工，人工只在规则允许的范围内决定。

4.3 两个开关的组合矩阵

组合 ① 统一定价开 + 入库审核关（推荐默认）

  • 价格规则由系统自动执行，不打扰人
  • 异常单（高价/低价未定价）才送审
  • 默认建议：全门店先落在这一档，运营一段时间再决定是否升档

组合 ② 统一定价开 + 入库审核开（最严）

  • 价格规则先跑，通过的单据仍需人工确认才入库
  • 价格差异 + 单据内容合并为一次审核，不让店员等两次
  • 适合新店、高值品类、需要磨合的阶段

组合 ③ 统一定价关 + 入库审核关（demo 现状）

  • 不校验价格、不审核——入库价随手填
  • 仅建议在试用阶段临时使用，事后手动核对账单

组合 ④ 统一定价关 + 入库审核开（过渡形态）

  • 没有定价表作基准，系统不判断贵贱
  • 全部单据由人看价格是否合理
  • 适合刚上线、定价表还没建起来时的过渡

4.4 配置层级：定价归门店，集团统一后续补（用户 09-08 拍板）

本期定调：定价与控制都按门店级实现。 原因：实际使用时每店面对的供应商、配送方式、谈判结果都不一样；强行企业级定价就是把所有门店拖慢、加运营成本。后续客户从「门店独立」演到「集团统一」时，只在集团层加配置与取价降级逻辑，不动门店已维护的数据——这是数据结构要预留的事。

为什么先做门店、后做集团：商品统一是集团定价的前提（用户 09-08 洞察）

企业统一定价最大的问题不是价格，是商品统一。 标准品有统一编码，无所谓；生鲜、散货自由度太大，很难做到统一。

这句话把"要不要集团统一"这个问题拆开了：集团定价能否落地，取决于商品主档是否真的统一，而不是价格规则怎么写。

商品类型 编码情况 能否进集团价
标准品（包装食品、日百、酒水） 69 条码 / 标准编码，天然唯一 能——集团价的主力覆盖范围
生鲜散货（蔬菜、散装肉禽、活鲜） 无印刷条码，靠各店自编内部码或口头叫法 很难——同名不同码、同码不同规格，统一编码本身就要先投入

结论：后续补集团统一时，集团价只覆盖有可靠编码的标准品；生鲜散货仍由各店自管。 这不是妥协，是承认现实——硬把散货塞进集团价，结果是门店为了过校验乱建商品，主档反而更脏。

因此本期的"门店独立定价"不是过渡态，而是散货的长期形态：即使将来集团统一上了，散货大概率还是各店自己定价。数据结构必须同时容得下"集团价（标准品）"和"门店价（散货）"两种来源。

归属 内容 本期 后续（集团统一）
门店级 采购定价 supply_price（scope='store'，storeId 必填）、成本控制 cost_control 实现 保留为兜底/例外
集团级（预留） 采购定价 supply_price（scope='group'，storeId 为空） 字段预留，不建数据 实现：取价降级 + 统一下发
企业级（仅共享） 商品主档 INV_GOODS（编码锚点）、商品别名 goods_alias（按店显示） 实现 实现

关键设计原则：

  • 门店与门店之间定价互不影响。A 店调价 / 关掉统一定价开关，不影响 B 店价格与管控
  • 门店可以跟随集团价（followGroup 字段，本期恒 false），后续集团统一定价时启用——跟随的门店自动同步集团价，未跟随的保留本店价
  • 门店价覆盖集团价（取价优先级：门店价 > 集团价，后续集团层启用后）
  • 成本控制与定价在同一层级（都是门店级），不会出现"统一定价开但定价归集团"的违和

4.4.1 相同商品在不同门店的名称差异——用编码锚定，不用名称

核心：定价锚点是商品编码，不是商品名称。 商品主档（企业级）保证 goodsCode 唯一；门店定价、门店别名各自维护，互不干扰。

  • 查价用编码（69 条码 / 内部 SKU 码），显示用门店别名
  • 同名不同码、同码不同名，一律以编码为准
  • 名称差异通过商品别名表解决：goods_alias = storeId + goodsCode + localName（6.1b）
场景 本期处理（v1.5 门店独立定价）
同一商品，A 店叫「土豆」、B 店叫「马铃薯」 同一编码，各店配别名，各自独立定价
不同商品，名字都叫「土豆」（各店自定义） 编码不同，各自独立定价，互不影响
散装商品没有条码 用企业内部 SKU 码建档，同样有唯一编码
门店自己起的俗称 进别名表，只影响显示，不影响定价

这样定价表就不需要为"名称差异"做任何特殊处理——名称从来不是它的键。后续集团统一定价也是按 goodsCode 统，不按名字统。

4.5 五条设计约定

  1. 默认按最严的高值场景设（未定价禁止、高价禁止、低价仅入库）。宁可让客户主动放开，也不要让客户不知道自己没管控。
  2. 价格提醒不可关闭（4.1.1）：开启统一定价就必须提醒，处理规则才可调。
  3. 改动留痕：配置谁改的、什么时候、从什么值改成什么值，全部写日志。成本控制是内控依据，必须可审计。
  4. 权限：仅管理员 / 采购经理可改配置，店长店员只读。审核权与配置权分开设——谁能审由角色权限判定（4.2），不写在门店配置里，所以"店长是审核人"不等于店长能改规则。
  5. 定价与控制同层（4.4）：本期定价与控制都在门店级，门店与门店之间互不影响。A 店关掉"统一定价"只是本店不校验价格、不改本店定价，与 B 店无关。

4.6 同入口的「售价与功能」：库存开关 + 改价管控（用户 09-08 定）

五、核心校验规则

以下为系统默认行为（按最严档设定）。实际行为由第四节「成本控制模块」的门店配置决定——客户可放宽三档处理规则，但价格提醒不可关闭（见 4.1.1）。

无定价 硬阻断 走「首单快速定价」建档后回填
送货价 > 定价 + 容差（疑似加价） 硬阻断 ① 申请调价（采购经理审批）② 拒收退货

|差| ≤ 容差 通过 按定价记成本、更新 avgCost

自采 / 临时零星 走例外通道 + 店长授权（可配） 例外通道

低价为什么也必须进定价体系？ 便宜了不拦，货照收——这是常识，拦着只会让货在门口烂掉。但定价表不回写，整套体系就废了：下次再送货还是按旧定价校验，异常会一直报；定价表与客户真实采购成本脱节，最后没人信它。所以低价也必须有一条回到定价体系的路径，只是不占用收货时间。

校验触发点： 入库单从"待提交"→"提交入库"的那一刻。保存为"待提交"不校验，提交时硬跑。

5.1 执行时机：配置先行，入库时执行，不做事后补票

客户能决定的是配置；系统做的是在入库时按配置执行。不是"先入库、再拿去审核"。

阶段 谁做 产出
① 配置（一次性，偶尔改） 客户：管理员 / 采购经理 采购配置：三档行为、容差、毛利率、审批人数…
② 入库（每次收货） 店员录送货价 → 点「提交入库」 系统当场按配置执行，实时给出结论
③ 例外处理（仅当配置要求） 采购经理 审批 / 处理知会，结论落回定价表

关键：校验发生在库存变动之前。 提交 → 校验 → 通过才写库存与批次。不通过时库存一个都没变，单据停在 15 价格异常。

先入库、后审核（不采用） 配置先行 + 入库时执行（本方案）
规则从哪来 审核人临时判断 客户提前配好
校验时机 入库之后 入库时（库存变动前）
成本记账 已按错误价记，要冲账 未通过则不记
库存影响 已混入，要倒查批次 未通过则不变
经理介入 每单都要看 只有异常单

采购经理介入只有两条路径，且都不等于"事后审核"：

  • 高价 → 单据被挡在入库之前，经理批的是"这批货能不能入"，批复前库存没动
  • 低价 → 入库时系统已当场判定并生成知会（不是事后人工翻账），经理处理的是"定价要不要更新"，与收货动作解耦、不占用收货时间；若客户认为低价也必须先确认才收货，把 lowAction 配成「阻断」即可

容差（消除抹零与分位误差，数值可配，见第四节）：

  • 单行容差：max(0.05 元, 定价 × 1%)
  • 整单容差：max(1 元, 总额 × 0.5%)——任一行超容差即逐行拦截，整单容差仅用于汇总显示
    （容差可在附录 A 高级选项中按门店调整）

6.1.1 父子继承模型（v1.19 起废弃，本节保留为决策记录）

⚠️ 本节方案已于 v1.19 废弃，定价对象统一为商品。 保留原文是因为它记录了一轮完整的论证与推翻过程，避免后人重走。 废弃依据（09-08 实测数据）： 四级分类 28 条 L4 中，19 个 L3 里有 15 个（79%）下面只挂一个 L4（西红柿、五花肉、鸡蛋、草鱼…都是孤节点），定在 L4 上 ≡ 定在单品上，父子继承是空转；而真正挂了多个 L4 的 L3（叶菜 7 个、根茎 2 个、淡水鱼 2 个、食用油 2 个），类内商品价差悬殊——娃娃菜 2.80 / 上海青 2.20（差 27%）、土豆 3.40 / 白萝卜 1.60（差 113%），根本不可能共用一个价。 代价却是实打实的：取价要跑五级降级、列表要为两种层级准备两套列、还有父子覆盖的例外逻辑。 替代： 多商品同价用批量添加（6.1.3），落库仍是每条商品一条；分类退化为筛选维度。

以下为原方案（已不执行）：

不需要为"统一"和"独立"各做一套——区别只在于定价定在哪一级。

父级是「四级分类 L4 节点」，不是标准商品。（09-08 修正） 散装蔬菜没有品牌、没有包装，不可能有对应的标准商品（stdId），但一定能挂到分类上——生鲜/蔬菜/叶菜/胶东白菜。分类是标准基础设施，商品可以千变万化，但都能归到分类上。这就是生鲜也能参与统一定价的原因。

结论修正（推翻上一版）：生鲜不是"统不了"，是"当时分类没建到那么细"。 分类细化到具体产品后（青麻叶 / 崇明 / 胶东 / 洛阳白菜各自一个 L4），生鲜完全可以按分类统一定价——因为产地、品种这些真实的价格影响因素，本来就应该体现在分类层级里。

6.1.2 品质维度：统一定价绕不开的第二个变量（09-08 新增）

分类解决了"品种不同价格不同"，但没解决"同品种品质不同价格也不同"。 同样是 生鲜/蔬菜/叶菜/胶东白菜，一级菜和二级菜、有机和普通，进价能差 20~40%——远超容差范围，不可能靠容差吸收。所以品质必须进定价键。

维度 是什么 稳定吗 放在哪
分类（L1~L4） 品种、产地、部位 稳定，建一次长期用 分类树
品质（grade） 成色、等级、认证 每批都可能变 独立字段，不进分类树

为什么品质不能建成 L5 分类： 分类是稳定的基础设施，品质是每批货的采购判断。把品质塞进分类树，会出现「胶东白菜/一级」「胶东白菜/二级」这种无限膨胀的分支，且同一商品不同批次要切来切去——分类树会被品质维度撑爆。所以 grade 是平行于分类的独立字段。

匹配与降级规则：

定价键 = (supId, refType, refId, grade, scope, storeId)

查价顺序（每个层级内部先精确后通用）：
  ① 子级 goods + grade='A'     → 命中即用
  ② 子级 goods + grade=''      → 未分级通用价
  ③ 父级 cat   + grade='A'     → 命中即用
  ④ 父级 cat   + grade=''      → 未分级通用价
  ⑤ 无定价 → noPriceAction

四条落地约定：

  1. 默认不启用：grade 恒为 ''，客户不做品质分级时逻辑与现在完全一致，零额外成本
  2. 枚举值客户自维护，不做自由输入：A/B/C、一级/二级、有机/绿色/普通 都行，但必须是下拉选。自由输入会重蹈"名称匹配不上"的覆辙
  3. 入库时可覆盖：商品档案存 defaultGrade（本店长期卖什么成色），入库时录入人可按当批实际情况调整——品质是收货那一刻看到的，档案只是默认值
  4. 品质差异走"仅本次改价"，不改定价：这批菜成色差、临时降价收了，是这一批的事，不能因此把"胶东白菜"的定价改成二级菜价（见 4.1 审批动作）。定价改不改，走调价单单独决策

6.1.3 定价时间轴：历史价、当前价、未来价（09-08 新增）

起因（用户原话）：「如果有生效日期的话，是否还应该有当前价格等信息，否则在生效之前的价格就无法查证」。

这条指出了一个真实缺陷：定价带 effFrom，但界面只显示「×年×月×日起」，历史价虽然在库里却查不到——等于没有可追溯性。修法不是补一个"当前价"列，而是把整条时间轴暴露出来。

三条规则：

  1. 状态一律按「今天」算，不用手工 status 字段 spPriceState(p)：比较 effFrom / effTo 与今天 → pending 待生效 / active 生效中 / expired 已失效。 手工 status 会与实际区间脱节（到了生效日没人去改它），"列表看到的"必须等于"入库时真正取到的"。

  2. 一行一条记录，三段价都在列表里 历史价不删、不隐藏。状态筛选默认"生效中 + 待生效"（日常视角），可切"全部（含已失效）"查历史。 effTo = 9999-12-31 显示为「长期」。

  3. 生效行标注下一条待生效价 如土豆当前 ¥3.55（09-01 ~ 09-30），已排了 10-01 起 ¥3.60，则在定价单元格下方小字显示「10-01 起 ¥3.60」——不切筛选也能看到即将变动，避免"不知道下个月会涨价"。

旧价自动闭合 spPriceCloseOld()： 新价落库前，把同键（供应商 + 商品 + 门店 + 品质）的重叠区间收窄：

情况 处理
旧价在新价之前 旧价 effTo → 新价 effFrom 的前一天
旧价在新价之后（已排了更远的未来价） 新价 effTo → 旧价 effFrom 的前一天
旧价完全被新价覆盖 同上第一条，旧价缩为短区间（不删除）

区间不留缝、不重叠，旧记录一律保留——按采购当时的定价反查成本始终可行。

示例（demo 种子数据，土豆 S2001）：

2026-01-01 ~ 2026-08-31  ¥3.40   已失效
2026-09-01 ~ 2026-09-30  ¥3.55   生效中   ← 入库校验取这条
2026-10-01 ~ 9999-12-31  ¥3.60   待生效

取价验证：msSupplyGetPrice(…, '2026-08-15') → 3.40；'2026-09-08' → 3.55；'2026-10-05' → 3.60。

残留风险（不追确认，供客户知悉）：品质靠人眼判断，供应商和门店对"A 级还是 B 级"容易扯皮。系统只能记录谁在什么时间判的什么级，不解决争议本身——这是线下管理问题。

七、调价联动售价（防"进价改了售价没改"）

调价审批通过时，对每个商品执行：

curMargin = (sale - oldPrice) / sale
newMargin = (sale - newPrice) / sale
if newMargin < targetMargin (15%, 可配) → 强制弹窗：
    提示：「新进价 ¥X，售价 ¥Y，新毛利率 Z%（< 目标 15%）」
    选项：[按建议售价 ¥Z 上调]  [手动输入新售价]  [已知悉，暂不调售价（记账）]

"已知悉暂不调"也要有结果： 生成一条「售价待调整」待办任务，挂在调价单上，下次同商品进价或月度盘点时再次提醒。

目的： 不是逼着改售价，而是确保毛利异常时有人背书。要么调价、要么留痕接受低毛利，绝不让进价调整默默发生。

八、入库单状态机扩展

新增  15 价格异常     25 待入库审核     30 已拒收
        ↑                  ↑                ↑
        └─ 高价拦截       └─ 入库审核        └─ 拒收
   ┌────────────────────────────────────────────────────┐
10 待提交 ──→ 15 价格异常 ──→ 调价审批通过 → 回到 10（重新走校验）
   │              │                    调价审批驳回 → 30 已拒收
   │              └─ 首单快速定价 → 回到 10
   ├──→ 25 待入库审核 （入库审核开关开启时，规则通过的单据也要人工确认）
   │              └─ 审核通过 → 20 已完成
   │              └─ 审核驳回 → 30 已拒收（可改为编辑后重提）
   └──→ 20 已完成 （一致 / 赠品 / 自采）
         低价 → 20 已完成 **+ 生成「价格异常知会」（采购经理必处理）**

关键路由规则（成本控制模块的两个开关决定）：

unifiedPrice.enabled entryAudit.enabled 状态机行为
关 关 10 → 20（自由，最快）
开 关 10 → 15（异常）/ 20（通过/赠品/自采/低价）
关 开 10 → 25 待入库审核 → 20 / 30
开 开 异常：10 → 15（审异常）/ 通过：10 → 25（审单据）→ 20

两个开关都开时，审核合并为一次： - 价格异常的 → 走 15 异常态，采购经理审 - 价格正常的 → 走 25 待入库审核，店长审 - 同一次入库只审一次，审核页同时展示价格差异 + 单据内容，不让店员等两次审批

15 价格异常 状态下： - 仍可编辑明细（改价、改数量） - 调价审批中不可再点提交，需等审批结论回来 - 在入库列表里加颜色标识（黄/红），方便跟单

25 待入库审核 状态下： - 单据已通过价格规则校验，等待人工审核入库（4.3 组合 ②/④ 启用） - 审核人能看到价格快照 + 单据内容，一次审批给结论 - 驳回时回到 10 待提交，店员可编辑后重提（不直接 30 已拒收——驳回不等于拒收）

30 已拒收 终态，但保留整单信息供事后查询；与供应商对账时作为"拒收依据"。

8.1 价格异常知会（低价场景）

低价不阻断收货，但必须留下一条必须由采购经理闭环的记录，否则定价表会与实际采购成本长期脱节。

priceNotice = {
  noticeId,
  entryNo, supplier, goodsCode, goodsName,
  quotedPrice, sentPrice, diff, diffPct,   // 定价 / 实收 / 差异
  createdAt,
  status,        // 10 待处理 / 20 已确认临时价 / 30 已更新定价 / 40 标记误报
  handler, handleAt, handleNote
}

处理三选一：

动作 结果
确认临时价 仅本次有效，定价不变；入库单标记已确认
更新定价 走调价单（降价也要审），通过后 supply_price 更新
标记误报 如录入错误、规格不同导致的假差异，填原因后关闭

闭环要求： 未处理知会数量在采购/库存首页红点提示；超过 noticeEscDays（默认 3 天）未处理 → 升级提醒（配置里可关）。

0. 版本更新记录

1. 背景与目标

超市采购策略：先定价，再入库。

  1. 与供应商先协定价格，形成「定价（协议价）」；
  2. 供应商送货时，门店按送货单录入实际进货价；
  3. 送货价与定价一致才允许入库——防止供应商擅自加价；
  4. 价格不一致时，需由采购经理修改定价，先定后入；
  5. 顺带管控：防止进货价修改后商品售价未及时调整。

目标：把"采购价"从入库单里的一个可随意改的字段，升级为有协议、有审批、有历史可查证的经营数据。

2. 用户与场景

角色 使用场景 权限

采购经理 处理价格异常审批（价格审批页），修改定价 采购定价 + 价格审批页

4. 详细功能需求

4.1 定价列表

  • 一行一个商品：主键为（商品 + 门店），一个商品在同一店永远只一条主表。
  • 列：序号 / 销售品名 / 系统品名 / 编码 / 规格（称重商品显示「称重/kg」）/ 分类 / 门店 / 当前定价（供应商 · 价格 · 生效起）/ 下一段（供应商 · 价格 · 生效日，未设置显 —）/ 操作。
  • 销售品名 = 门店商品名（可带品牌与俗称）；系统品名 = 标准商品规范名（学名）。两者不同属正常（土豆/马铃薯、西红柿/番茄）。关联键是商品编码，不是名称。
  • 筛选：门店、供应商、关键词；门店/供应商为胶囊样式选择器。
  • 操作列只保留：编辑 / 趋势（新增走批量添加；历史信息由趋势图承载）。
  • 供应商延续是默认：编辑时供应商输入框预填当前值，改就改、不改就沿用，无强制确认。

4.2 批量添加（新增定价唯一入口）

流程：选门店（在前）→ 选供应商 → 选生效日期 → 按分类/关键词筛选商品 → 勾选 → 填价（「统一价填充」或逐行改）→ 保存。

  • 勾选与填价是两个独立状态：填价自动勾选；全选未填价时计数提示「N 个未填价」。
  • 保存分流（按生效日期）：
  • 生效日期 ≤ 今天：旧价归档写历史，主表更新为当前价；
  • 生效日期 > 今天：只写下一段（待生效），当前价完全不动，到期自动切换。
  • 已存在当前定价的商品标黄提示，走"调价"归档流程。
  • 切换门店清空已勾选（价格是门店维度，禁止跨店误写）。
  • 弹窗高度固定（表格区 340px），筛选后数据变少不改变弹窗高度。
  • 门店/供应商选择器为胶囊样式（白底圆角 + 加粗主蓝值 + ▼），顺序：门店 > 供应商。
  • 弹窗打开即显示各商品当前定价（不依赖先选供应商）。

4.3 编辑定价

  • 弹窗 = 当前段 + 下一段一站式：改当前价和设未来价一次完成，无独立"设下一段"入口。
  • 当前段：供应商（预填）/ 价格 / 生效日期；下一段（可空）：下一供应商（预填当前供应商）/ 下一价 / 下一起效日。
  • 保存规则：
  • 供应商不变、价格变 → 旧价写历史（关闭原因「调价」）；
  • 供应商变 → 旧段写历史（「换供应商」），旧的下一段连带归档（避免取价仍命中）；
  • 生效日期为空兜底为今天。
  • 删除：当前段写历史（保留可查），主表移除。

4.4 价格趋势

  • 阶梯折线：定价是阶梯函数——每段从生效日水平延续到下一段生效日，变价日竖直跳变；两变价点之间不画斜线。
  • 真实时间轴：横轴按日期毫秒值定位，段间距真实反映时间间隔（不允许 8 个月和 1 天等宽）。
  • 延续到今天：当前价一直画到今天，不在最后一次变价日截断；设置了待生效价时，今天之后的延续段画虚线。
  • 入库散点（菱形）：位置 =（入库日期，实际入库价），与定价线对照——散点偏离折线即采价异常；tooltip 显示数量×单价+批次号。
  • 线段颜色跟随该段生效的供应商，弹窗顶部彩色 key 标供应商。

4.5 管控配置（门店级，与定价联动）

入口：门店管理 → 行内「管控配置」，双 Tab（售价与功能在前、进价管控在后）。

配置 取值 联动
库存开关 开/关 进价管控的前提：关 → 进价管控整块置灰
收银改价 / 打码改价 允许/临时（仅当次）/禁止 独立于库存开关
统一定价 开/关 开启后入库单必须命中定价；有统一定价但零定价 → 红条告警（全店入库停摆）
入库审核 开/关 所有入库单需审核确认后才入库（与价格无关）；审核人由角色权限决定，不在配置里指定

说明文案规则：每条说明只回答「去哪配 / 会怎样」，不解释「为什么这么设计」；开发未实现项标「开发提醒」（橙），与「产品说明」（蓝）视觉区分。

4.6 入库价格校验（执行时机：配置先行，入库时执行）

  • 开启统一定价后，入库单保存前按（供应商 + 商品 + 门店）取定价：一致才允许入库。
  • 价格提醒是硬性的：开启统一定价就必须提醒，四个展示位置（列表行/详情/提交拦截/告警），不可配置关闭。
  • 价格不一致：拦截入库，走加急审批（价格审批页），不是"先入后补"。
  • 统一定价开启但商品无定价：按管控配置的处理规则执行（禁止入库 / 仅提醒），零定价+禁止=全店停摆，管控配置弹窗红条告警。

5. 业务规则

  1. 先定后入：定价先行，入库校验在库存变动之前执行，不做事后补票。
  2. 取价：按主表精确匹配（商品+门店），无分类继承、无降级链。当前段命中时若下一段生效日已到且供应商匹配则取下一段价；换供应商场景同理。
  3. 旧价自动闭合：调价/换供应商时旧段写历史（不可变），历史价始终可反查；任何操作不物理删除历史。
  4. 状态按今天算：待生效 / 生效中 / 已失效由生效区间与当天比较得出，不用手工状态字段。
  5. 配置层级：定价与管控都归门店（门店独立维护价格）；集团统一价字段已预留（scope='group' 等），本版不做。
  6. 编码锚定：同商品跨门店名称可能不同，关联一律用商品编码 + 标准商品库，不用名称。
